Secure by Design

Every artifact, every tool call, every line of agent-generated code runs inside your infrastructure — with no trust granted by default

Cosmogony's security model starts from a single principle: agent execution is untrusted code running in your environment. The platform is architected to contain it, audit it, and attribute it — without slowing down your engineers.

Execution Happens Entirely in Your Infrastructure

No code runs in-client. No build runs on Cosmogony's servers unless you host Cosmogony there. Agent sessions run in ephemeral containers provisioned inside your environment — your cloud account, your VPC, your security perimeter. Your data classification policies, network controls, and DLP tooling apply without exception.

Isolated Sandboxes Per Session

Each session gets its own ephemeral container provisioned at session start and destroyed at session end. Containers are namespaced to the session — they cannot communicate with each other, cannot access the host filesystem, and have no visibility into other users' sessions or credentials.

Process isolation

Separate container per session, non-root user. No Docker socket mount. No host filesystem access.

Resource limits

CPU, memory, PID count, and disk enforced by the platform via cgroups. Runaway builds cannot starve your infrastructure.

Kernel hardening

seccomp default profile, no CAP_SYS_ADMIN, no ptrace. Containers run with the smallest possible privilege surface.

Secret isolation

No backend environment variables or database credentials are injected into the sandbox. Secrets never reach the execution environment.

Temporal isolation

Containers are destroyed on session end, inactivity timeout, or failure. No state persists between sessions.

Inter-container isolation

Each sandbox runs on its own Docker network. No inter-container communication is possible regardless of configuration.

Containers Live Once — Zero Drift

Cosmogony runs on a YOLO (You Only Live Once) container model. There are no long-running, patched-in-place build environments that accumulate drift. Every session starts from a known, versioned, CI-built image. If a container is destroyed — through a session end, a timeout, or a failure — the next session starts from scratch. Your backend infrastructure and client devices are never modified by agent activity.

Network Egress Is Deny-by-Default

Sandbox containers run on an isolated Docker network with iptables egress rules enforced at container creation. By default, only package registries (npm, pypi, Maven, Gradle) and your project's git remote are reachable. All other outbound traffic is dropped.

What this means in practice: an agent that has been prompt-injected to call an arbitrary endpoint hits a hard network block, not just a policy check. The defence is enforced at the kernel level, below the application layer.

Org admins configure additional allowed endpoints through the platform. No in-repo file and no agent action can extend or override the network policy.

Mandatory Tool Registry — No Phantom Tools

Agents can only call MCP-registered tools that an org admin has explicitly permitted. The tool registry is deny-by-default: a server or tool that hasn't been registered simply doesn't exist from the agent's perspective.

This provides structural protection against prompt injection attacks. An attacker cannot trick an agent into calling an arbitrary endpoint, because the agent has no mechanism to reach anything outside the registry. Enforcement runs at four independent layers:

  • ADK dispatch — the agent can only call functions registered at session start. Hallucinated tool names are rejected at the framework level.
  • Proxy server validation — every tool call validates the server name against the registry. Unknown servers return 403, not 404 (no information leakage about what exists).
  • Proxy tool validation — every tool call validates the tool name against the per-server allowlist.
  • Network isolation — even if all three layers above were bypassed, the agent container has no outbound network path to any non-registered endpoint.

Per-User Identity for External Integrations

When an agent calls Jira or Slack on your behalf, it does so as you, not as a shared service account. OAuth tokens are stored per-user, encrypted at rest via KMS, and automatically refreshed. External systems see requests attributed to the correct user — correct permissions, correct audit trails in those systems. No "Cosmogony Bot" flooding your changelogs.

If a token is revoked externally or expires without a valid refresh, the integration is marked as needing re-authorisation and the agent surfaces this to you rather than failing silently or falling back to a service account.

Agents Work in the Open

Every command an agent executes, every file it modifies, every tool it calls is logged with full attribution — session ID, user ID, timestamp, exit code, and network bytes. The audit log is append-only.

Agents work on feature branches, never directly on your default branch. All changes arrive as pull requests that your team reviews and approves before they land. The platform's guardrail system enforces this in code — git push to main is blocked at the command level, not just in the instructions.

Code-Immutable Safety Guardrails

The agent's safety constraints are enforced by a pure function that runs below the LLM — not as prompt instructions the model could reason its way around. Before any shell command executes in the sandbox, the guardrail evaluates it against a code-immutable ruleset:

  • Git sync operations (push, pull, fetch, clone) — version control is platform-managed
  • History rewrite or force operations — --force, filter-branch, reset --hard against a remote
  • Destructive filesystem operations outside /workspace
  • Platform credential access — reading GIT_AUTH_TOKEN or equivalent environment variables
  • Fork bombs and mass permission changes

A blocked command returns steer guidance to the agent so it self-corrects. It is never a silent failure or an infinite retry loop.

Compliance-Ready Audit Trail

The platform's audit model is designed for ISO 27001 and SOX environments. Every agent action, tool call, and file change is stored in an append-only audit log with full attribution. Gate results — the deterministic build and test verdicts that control stage completion — are recorded with their profile version, so you can reconstruct exactly what was run and what passed. Session containers leave no residue: no credentials in environment variables, no persistent state outside the git repository.

The platform runs in fully air-gapped environments where no external network access is permitted. Package registries can be pointed at internal mirrors; all Cosmogony components run within your perimeter.
