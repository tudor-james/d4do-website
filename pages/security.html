Secure by Design

The fundamental security problem with agentic AI — and how Cosmogony solves it at the architecture level

The Problem Every Other Agentic Tool Has

Most AI coding tools — Cursor, Copilot, local Devin variants, IDE-embedded agents — execute agent-generated code on your machine, inside your IDE process, or in a shared cloud environment. That means:

Agent runs on your laptop

The agent has access to your filesystem, your environment variables, your SSH keys, your AWS credentials, your browser sessions. A prompt injection in a file it reads can exfiltrate everything reachable from your terminal.

Agent runs in your CI/CD pipeline

Better than local, but the agent inherits pipeline secrets, deployment credentials, and production access scopes. A malicious dependency or injected instruction runs with the same trust as your automation.

Agent runs on the vendor's cloud

Your code, your secrets, and your data leave your perimeter. You depend on the vendor's security controls, their network isolation, and their compliance posture — not your own.

The root cause: these tools treat agent-generated code as trusted. Cosmogony treats it as untrusted by default — and enforces that at the infrastructure level, not with instructions the model can reason its way around.

The Cosmogony Architecture: Server-Side Sandboxes in Your Infrastructure

Every agent action in Cosmogony executes inside an ephemeral, isolated container provisioned within your hosted infrastructure — not on your client device, not in your CI pipeline, and not on Cosmogony's servers. The agent never runs where your credentials live.

Your infrastructure, your perimeter

Cosmogony deploys into your cloud account or on-premises environment. Your data classification policies, network controls, and DLP tooling apply without exception. Nothing leaves your perimeter.

One container per session

Each agent session gets its own isolated container, created fresh at session start and destroyed at session end. Sessions cannot see each other, cannot share state, and cannot access the host.

No credentials in the sandbox

Backend secrets, database credentials, and API keys are never injected into the execution container. The agent cannot exfiltrate what it cannot see.

No client-side execution

Nothing the agent generates runs on your laptop or workstation. Your local machine is a UI — it never becomes an execution environment for untrusted code.

Containers live once

No long-running environments that accumulate drift or persist state. Every session starts from a versioned, CI-built image. Worst case is a destroyed container, not a compromised host.

Works air-gapped

All Cosmogony components run within your perimeter with no external network dependencies. Package registries point at internal mirrors. No data transits the public internet.

Network Egress Is Deny-by-Default

Sandbox containers run on an isolated Docker network with iptables egress rules enforced at container creation — below the application layer, not as a policy the agent could override. By default, only package registries (npm, pypi, Maven, Gradle) and your project's git remote are reachable. All other outbound traffic is dropped at the kernel level.

Why this matters for prompt injection: if an attacker embeds instructions in a file the agent reads — telling it to exfiltrate data to an external endpoint — the network DROP means that call never leaves the container, regardless of what the agent tries to do. The defence is architectural, not behavioural.

Org admins configure additional allowed endpoints through the platform. No in-repo file and no agent action can extend or override the network policy.

Mandatory Tool Registry — No Phantom Tools

Agents can only call tools that an org admin has explicitly registered. The registry is deny-by-default: an unregistered server or tool doesn't exist from the agent's perspective. Enforcement runs at four independent layers so that bypassing one doesn't compromise the system:

  • Framework dispatch — the agent can only call functions registered at session start. Hallucinated tool names fail immediately.
  • Proxy server validation — every call validates the server against the registry. Unknown servers return 403, not 404, so the registry contents are never leaked.
  • Proxy tool validation — every call validates the specific tool against the per-server allowlist.
  • Network isolation — even if all three layers above were bypassed, the sandbox has no outbound network path to any non-registered endpoint.

Code-Immutable Safety Guardrails

Safety constraints are enforced by a pure function that runs below the LLM — not as prompt instructions the model could ignore under pressure. Before any shell command executes in the sandbox, it is evaluated against a code-immutable ruleset. Commands that would push to your default branch, rewrite git history, access credential environment variables, or destroy the workspace are blocked and return corrective guidance to the agent. They never execute silently.

Agents work on feature branches only. Version control is platform-managed — the platform opens the PR, you approve the merge. No agent can push directly to your main branch.

Per-User Identity for External Integrations

When an agent calls Jira or Slack on your behalf, it does so as you — not as a shared service account. OAuth tokens are per-user, encrypted at rest, and automatically refreshed. External systems see actions attributed to the correct person with correct permissions. No shared bot credentials with over-provisioned access.

Full Audit Trail

Every command executed, every file modified, every tool called is logged with full attribution — session ID, user ID, timestamp, exit code, and network bytes. The audit log is append-only. Gate results recording exactly what was built and what passed are stored with their profile version. The platform is designed for ISO 27001 and SOX environments from day one.
