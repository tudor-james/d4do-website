Aligns to Your Policies and Processes

Cosmogony works inside your existing infrastructure. It doesn't ask you to change your engineering process — it runs inside it.

Works With Your Existing Infrastructure

You bring the repository, the CI/CD pipeline, the cloud account, and optionally the model. Cosmogony works on the branch you give it and opens a pull request when the work is ready. Your existing pipeline — whatever you run — is untouched and remains the authority for what ships to production.

Cosmogony owns its branch, you own the merge. The platform works on a dedicated session branch. It commits, pushes, and opens a pull request. You review the PR exactly as you would any team member's contribution. The default branch is protected — no agent can push to it directly, enforced in code, not just in the agent's instructions.

Bring Your Own Model

Cosmogony is model-agnostic and runs multiple models within a single workflow. Different stages can use different models optimised for the task — a cheaper, faster model for triage and gate classification; a more capable model for design and planning; a balanced model for development. This gives you control over cost, latency, and sustainability without sacrificing output quality.

Running multiple models also means no single provider lock-in. If a model improves, degrades, or a better option emerges for a specific task, you can swap it at the stage level without changing the workflow or retraining the system.

Enterprise Integrations

Cosmogony integrates with the tools your team already uses for requirements and project management.

Issue Trackers

Start a session directly from a ticket. The requirements agent reads the ticket, asks clarifying questions, and produces a specification. As work progresses, the agent updates status and posts progress comments. When the PR opens, the ticket is linked.

Documentation Platforms

Start with business requirements written in your documentation system. The agent reads the page, extracts intent, and grounds the specification in your documented context. Completed design documents can be written back.

Source Control

Issues become sessions. Commits reference the issue. PRs close it on merge. The full lifecycle is traceable from business requirement to deployed code, with no manual linking required.

Team Messaging

Agents post status updates to configured channels at gate transitions — keeping the team informed without requiring them to monitor the platform UI.

All integrations are configured by org admins through the integration registry. Individual users connect their own OAuth accounts, so actions are attributed correctly to the right person in every external system. Admins control which integrations are enabled, which tools are permitted, and what rate limits apply.

Customisable to Your Engineering Culture

Per-Stack Build Profiles

Cosmogony ships with platform-defined build profiles for common technology stacks. Each profile defines the exact commands used for install, build, lint, typecheck, test, and acceptance verification. Profiles are versioned in the platform and can be overridden by org admins for stacks with non-standard conventions. Agents follow the profile's playbook — they don't invent build commands or bypass the canonical toolchain.

This matters because it closes a common attack surface: a repository that redefines what "test" means cannot fool the gate. The platform runs its own verified commands, not the repo's scripts.

Agent Behaviour Is Steerable

Prompt extensions at org, team, and project level let you encode your architectural decisions, coding standards, and workflow conventions directly into the agent instructions. These are admin-managed and version-controlled in the platform, not in the repository where an agent could accidentally modify them. Common uses include:

  • Coding standards — frameworks, patterns, and libraries your codebase uses
  • Architecture decisions — authentication approach, database access patterns, naming conventions
  • Build conventions — non-standard toolchain commands for your specific project setup
  • Security policies — what the agent is and is not permitted to do in your environment

SDLC Alignment

The four-stage workflow maps naturally to most delivery frameworks. Gate behaviour — whether approval is required, who can approve, and what constitutes a passing gate — is configurable per project type. Teams that want more autonomy can reduce gate friction; teams with stricter governance can require explicit sign-off at every stage.

Cosmogony uses your existing CI/CD pipelines and governance. The platform doesn't replace your pipeline — it feeds it. The PR that emerges from a Cosmogony session goes through exactly the same review, approval, and deployment process as any other PR on your team.

Works in Fully Air-Gapped Environments

All Cosmogony components can run within your perimeter with no external network dependencies. Package registries can be pointed at internal mirrors. Model inference can be directed at on-premises or VPC-hosted endpoints. The platform has no dependency on Cosmogony's own cloud infrastructure once deployed in your environment.

This makes Cosmogony compatible with environments that prohibit outbound internet access, including defence, financial services, healthcare, and other regulated sectors where data never leaves the controlled perimeter.
